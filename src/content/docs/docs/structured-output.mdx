Observers at our wildlife station don’t write rows. They write notes, in their
own words: “Three badgers came through overnight, one of them limping.” The
station keeps rows: a species, a count, a place, the kind of records its
assistant searches in [Call your own functions](/docs/function-tools/).
Someone has to turn one into the other. On this page, the model does it, in a
shape your program can read.

On this page you’ll:

- see why a good answer for a person is a poor one for a program;
- describe the shape you want as a **schema**;
- read the answer as data, in your language;
- meet the most common schema mistake: an answer that fits and is wrong;
- see which providers can hold a model to a schema.

The answers shown are real: we ran each step with `gpt-5.6-sol` through OpenAI
Codex. The short examples build on one another; the
[whole program](#the-whole-program) near the end has everything in one piece.

Instead, tell the model the shape of the answer.

## Describe the shape

A **schema** describes a piece of data: which fields it has, and what each may
hold. Think of it as a form the model must fill in. Ours has one line per
sighting:

| Field | What belongs there |
| --- | --- |
| `species` | Text: the animal’s common name, singular |
| `count` | A whole number: how many animals |
| `place` | One of the station’s three places |

Here it is as code. The station’s places are listed once, at the top:

<DocsExample recipe="so-schema" />

Read it from the outside in. The answer is an object with one field,
`sightings`, which is a list (an `array`). Each item in the list is an object
with the three fields above. Then three words do most of the work:

- **`required`** lists the fields that must be there. Describing a field under
  `properties` doesn’t make it required; this list does.
- **`enum`** lists the values a field may take. Here, a place must be one of
  the station’s three.
- **`additionalProperties: false`** means no other fields: the model can’t add
  its own.

The description on `species` is for the model, like a tool input’s
description: it says how to write the name. This notation is JSON Schema, the
same one a tool’s inputs use. These few words are enough to start.

Look again at the list of places. A schema isn’t only the shape of the answer:
it is everything the model is *allowed* to say. We’ll come back to that.

## Ask for that shape

Put the schema in the request’s settings, as its answer format. `strict` asks
the provider to follow it exactly. The rest of the request is unchanged:

<DocsExample recipe="so-ask" />

<CapturedAnswer set="structured-output" step="ask" show="read" />

Exactly the form we described: two records, lower-case species, a place from
the list. This time it also took {s.ask.output_tokens} output tokens instead of
{s.plain.output_tokens}. That was true of these two runs; a schema isn’t a
promise to save tokens.

Notice what’s missing: the limping badger, and the times. The schema has no
field for them, so they’re gone. A schema is a choice about what to keep, not
only about how to lay it out. If the station tracks injuries, give injuries a
field. Either way, keep the original note: it’s the only complete record.

## Use the records

The answer is JSON in a shape you know, and LM15 reads it into your language’s
own values: dictionaries and lists, a JSON value, or, in Go, a struct you
declare. So the program uses the records directly:

<DocsExample recipe="so-use" />

With the answer above, every language prints:

<pre class="lm-code not-content"><code>{printed}</code></pre>

The count is a number the moment it arrives. Nothing searched the text for it.

Reading JSON isn’t checking it, though. Your language’s JSON reader turns text
into values; it doesn’t check every rule of the schema, and a type you declare
for the data is a promise you make, not a check. And an error, or an answer
cut short, is not an empty list of sightings. Look at the finish reason before
you store anything.

## A note that doesn’t fit

A different night, a different part of the station. Only the note changes:

<DocsExample recipe="so-note-barn" />

Before sending it, look at the schema’s places: oak grove, stream, meadow.
Where can the owl go?

<CapturedAnswer set="structured-output" step="trap" />

The owl was on the old barn roof. Our records now say it was in the
**{owl(s.trap).place}**.

Nothing failed. The answer has every field the schema asks for, and every value
it allows. It’s a **valid** record. It isn’t a **true** one, and nothing in
your program would ever notice: it sits in the station’s records looking
exactly like the badgers.

This isn’t one model’s quirk. We sent the same note, with the same schema, to
the other providers below. Every one that followed the schema put the owl
somewhere it wasn’t: OpenAI in the {owl(captures.providers['openai:gpt-5-mini'].trap).place},
Anthropic in the {owl(captures.providers['anthropic:claude-haiku-4-5'].trap).place},
Gemini in the {owl(captures.providers['gemini:gemini-2.5-flash'].trap).place}, and
OpenRouter’s model in the {owl(captures.providers['openrouter:openai/gpt-4o-mini'].trap).place}.
And it isn’t the model’s fault. We asked for one of three places and the barn
isn’t one of them. A form with no honest box gets filled in anyway.

**A schema controls the shape of an answer, not its truth.**

## Leave the model a way out

Give the model a way to say “none of these”: add `"other"` to the places.

<DocsExample recipe="so-schema-other" />

Send the barn note again:

<CapturedAnswer set="structured-output" step="fixed" />

The owl is now under **{owl(s.fixed).place}**, which is true. And your program
can find it: a record with place “other” is one a person should look at, or
send back to the observer. In our runs, every model that had the choice used
it for the owl.

Whenever a field is a closed list, ask what the model should answer when
nothing on the list is right, and make that answer allowed. The same goes for
any field the model *must* fill: a species nobody could name, a count nobody
made. A field that must be filled will be filled.

`other` isn’t a location, though: it only says “not one of these”. If you need
to know *where*, keep the observer’s own words in a text field alongside it.
And a list of places can’t say what each place *means*. The hares were in “the
barn field”. This model put them in the {hares(s.fixed).place}; other models,
in other runs, chose “other”. Both are fair if “meadow” means any grassy
field, and one is wrong if it names a single survey site. When the difference
matters, say what each place covers, in the schema’s descriptions or in the
instructions.

## When a provider can’t follow a schema

Not every provider can hold a model to a schema. We sent the same two requests
to six providers: the stream note with the fixed schema, and the barn note with
the original three places.

  <thead>

  </thead>
  <tbody>
    {rows.map((row) => (
      <tr><td>{row.name}</td><td><code>{row.model}</code></td><td>{row.schema}</td><td>{row.place}</td></tr>
    ))}
  </tbody>
</table>

Each provider takes a schema in its own form; LM15 translates yours, so the
request you write doesn’t change. After that, it depends on the provider:

- **Most follow it.** The answer has the shape you asked for.
- **Some refuse it.** DeepSeek answered with an error, “This response_format
  type is unavailable now”, and LM15 passes that error on to you.
- **Some would accept it and ignore it.** Z.AI takes the schema and writes
  whatever it likes: here, Markdown again. LM15 knows this about Z.AI and
  won’t let it happen silently. In Python, TypeScript, Rust and Go, it sends
  the request without the schema and records on the response what it left
  out, and why:

<pre class="lm-code not-content"><code>{captures.providers['zai:glm-4.5-air'].ask.adaptations[0].reason}</code></pre>

In R and Julia, the same request is refused before anything is sent. Either
way, you find out from your program, not from a row that looks fine.

That reason mentions the other answer format, `json_object`: any valid JSON.
It guarantees JSON, not your shape. Asked that way, DeepSeek answered with
fields of its own choosing:

<pre class="lm-code not-content"><code>{readableText(captures.extras.deepseek_json_object.text)}</code></pre>

Sensible fields, and none of them is `place`. “It’s valid JSON” is not “it’s
the record I asked for”. If your program needs the shape, use a schema, with a
provider that follows it.

These are results for these models on {new Date(`${captures.date}T12:00:00Z`).toLocaleDateString('en-US', { month: 'long', day: 'numeric', year: 'numeric', timeZone: 'UTC' })}, not a promise about every model a
provider offers.

## Try it yourself

Predict before you run each one.

1. Send this note, from the edge of the oak grove, with the fixed schema:
   *{TOUR.extract.notes.deer}* What will the model write as the species?
2. Take `"other"` out again, and send a note about a hedgehog in the station’s
   car park. Where will the hedgehog be recorded?
3. Keep the three places. Would a program that checks every answer against the
   schema catch the owl in the wrong place? What could?

<details>
<summary>What to expect</summary>

1. When we ran it, the model wrote **{s.deer.data.sightings[0].species}**: not
   roe, not fallow. Good: the note doesn’t settle the species, and the model
   didn’t pretend it did. Don’t count on it, though. If it matters, give the
   model a way to say it isn’t sure, as you gave it “other”.
2. At one of the three places: the car park isn’t on the list. The same trap
   as the owl.
3. No. The wrong place is an allowed value, so the answer passes every check.
   Only the note can show it’s wrong: keep the note with the record, and have a
   person look at anything uncertain.

</details>
