In this guide, you’ll learn to make your first model call with LM15. We’ll explain
what each step does and why LM15 works the way it does, so you can build on it.

Choose your **language, provider, and model** at the top left of the page. Changing
languages changes the code examples, not the explanation: LM15 uses the same
ideas across languages and providers. Your chosen provider and model appear in
the examples, ready to copy. Choose the provider your API key belongs to and a
model you can access.

This guide is for learning at your own pace. If you’d rather take another path:

- **Explore in your browser.** The [playground](/playground/) helps you get an API
  key, try a model, and copy the code to run on your computer.
- **Build with a coding agent.** Give it our [LM15 skill](/skill.md) or

LM15 is first and foremost a **contract**: a shared format for requests and
responses, with precise rules for what each field means. It also defines how
responses arrive piece by piece when streaming. Each language implementation
follows this contract, using the conventions of its language.

An **adapter** translates an LM15 request into the format a provider accepts,
then translates the answer back into an LM15 response. Your application works
with the contract; the adapter handles the provider’s details. Learn that one
contract, and you can use it across languages and providers without learning a
new request and response format each time. Providers still differ in what they
can do—the shared format does not erase those differences.

That common meeting point is useful on both sides. Application and framework
builders can use it without knowing every provider’s API. Someone connecting a
new model service can implement it without knowing every application that will
call it.

LM15 began with direct calls to provider APIs, but the contract does not require
a remote service. A custom adapter could connect to a model running inside your
program through PyTorch or vLLM. It could even connect to a coding agent that
runs its own tools and completes several steps before returning an answer.
These would be custom integrations, not connections LM15 currently supplies.

The responsibility is the same: read the LM15 request, carry out what it asks,
and return an answer that follows the response rules. If the system cannot
honor part of the request, report that rather than silently ignore it. Applications
can then use the connection through the same contract.

In a nutshell, a request describes what you want; a response records what came back:

```text
Request
  model · messages · system instructions · tools · settings
    ↓
Adapter ↔ model or service
    ↓
Response
  message · finish reason · usage
```

System instructions, tools, and settings are optional. With streaming, the same
request produces the answer piece by piece, followed by a final event carrying
the finish reason and any reported usage.

Each part of the request has its own smaller contract:

### Model: which model to call

`model` is a required, non-empty string naming the model you want. When using
the router, `provider:model` also names the provider to contact. The router
removes that prefix before passing the model name to the adapter.

A model name belongs to a particular service. Changing providers may require
changing the model name too.

### Messages: what the model receives

`messages` is an ordered list with at least one message. Each message contains:

- **A role:** `user`, `assistant`, `tool`, or `developer`—who the message is from.
- **Parts:** one or more pieces of content, each with its own type and fields.
  A text part holds text; an image part identifies an image; a tool-call part
  holds the call’s ID, function name, and input.

The role determines which parts belong in a message. For example, tool results
belong in tool messages, not user messages. To continue a conversation, include
previous messages and the new turn. Keep the full assistant message: it may
carry provider data needed for the next call, beyond the visible text.

The optional `system` field is separate from this list. It holds instructions
that apply to the request as a whole.

### Tools: what the model can use

`tools` lists the tools offered for this request. Each has a unique name and is
one of two kinds:

- **Function tool:** a name, an optional description, and a schema describing
  its inputs—their names, types, and which are required. The model can request
  a call; your application decides whether and how to execute it, then returns
  a result with the matching call ID.
- **Built-in tool:** a name and optional configuration for a tool the provider
  runs, such as web search. LM15 does not ask your application to run it again.

Declaring a tool makes it available; it does not require the model to use it.
Tool-choice settings control that separately.

### Settings: how to generate the answer

`config` holds optional settings such as the output-token limit, temperature,
response format, reasoning effort, caching, and tool choice. Each setting has
its own allowed values and rules. For example, a token limit must be positive;
a tool-choice restriction can only name tools offered in the request.

Leaving a setting out is different from setting it to zero or switching it off.
It means you have not requested a value. A valid setting still needs support
from the chosen provider and model; provider-specific options go in
`config.extensions`.

## Capabilities

What can we express through this contract? LM15 is not limited to the features
that every provider has in common. Features shared by multiple providers have
common fields; provider-specific options belong in **extensions**, where you
can use the provider’s own names and values. On the response side,
**provider_data** preserves the provider’s original answer alongside the shared
response fields.

That separation is useful: it makes clear where your code relies on a
provider-specific option rather than a shared feature. Shared does not mean
universal, though—you still need a model and provider that support what you ask.

The shared capabilities include:

- **Streaming**
- **Tools**
- **Structured output**
- **Reasoning and continuation**
- **Prompt caching**
- **Media**
- **Errors and usage**

Separate APIs cover files, batches, media generation, video jobs, and realtime
sessions. These surfaces remain provisional.

A shared interface does not make every provider identical. Availability and
behavior depend on the endpoint, model, and SDK. An official SDK may expose
features or new endpoints that LM15 does not yet support. Selecting a combination
above is not a guarantee that every feature works with it.

## Check the behavior before depending on it

LM15 defines its common behavior in a language-neutral contract. Shared fixtures
check request construction, response parsing, streaming, serialization, and
errors across implementations.

The contract has authority over the implementations—not the other way around.
You can check an SDK against defined behavior instead of assuming that similar
method names mean the same thing.

Use test responses to exercise your own integration without spending provider
credits. Run real provider calls when you need to verify the network path and
the behavior of a particular model.

Fixture checks, executable examples, and live provider captures answer different
questions. Check the evidence for the SDK and feature you intend to use; a
passing recorded case is not a promise about every model or future API change.

## Small enough to build on

The Python core has **no required third-party dependencies**. WebSocket support
is an optional extra.

Evaluate LM15 alongside the official SDKs you would otherwise install: required
dependencies, installed size, startup time, memory, and request/stream processing
overhead.

Benchmark reports identify the SDK version, runtime, workload, and environment.
A lower startup cost does not mean the model generates tokens faster. Compare
the costs that matter to your deployment, with the features you actually use.
