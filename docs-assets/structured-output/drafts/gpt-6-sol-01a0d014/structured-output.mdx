At the wildlife station, observers write what they saw in their own words.
The station keeps sightings as records. To add a note to those records, you
need an answer your program can read: a species, a count, and a place for
each sighting.

In this guide, you’ll turn one note into records. Then you’ll try a note that
doesn’t fit the allowed places, see what goes wrong, and change the schema so
the model can give an honest answer.

Choose your language, provider, and model at the top of the page. The code
follows your selection. The answers below are **real recordings** from
`gpt-5.6-sol` through OpenAI Codex on 23 September 2026, not promises of what
your model will say. If you’re following along, run the snippets in order:
later snippets reuse names from earlier ones.

## Describe a record

A **schema** describes which fields an answer must have and what can go in
them. We want a list called `sightings`. Each item has a species name, an
integer count, and a place chosen from the station’s three named areas:

<DocsExample recipe="so-schema" />

The outer object has `sightings`; its value is an array. Each item in that
array is an object with three required fields. `additionalProperties: false`
means the model cannot add fields we haven’t named. The examples set
`strict: true` when requesting the answer, asking a provider that supports
it to follow this schema exactly.

Notice what the schema does **not** include: the badger’s limp or the time
of either sighting. They appeared in the table but have nowhere to go in
this record. Add fields for details you need to keep. A schema is a choice
about what to preserve, not only how to format it.

Nor do we ask the model for the filing date. The station already knows when
it received the note; your program can attach that date itself.

## What if a note doesn’t fit?

Try a different note. An owl was calling from the **old barn roof**; two
hares were in the barn field:

<DocsExample recipe="so-note-barn" />

Keep the three-place schema and run the request from *Ask for that shape*
again:

<CapturedAnswer set="structured-output" step="trap" />

The answer has the right fields and an allowed place for each animal. But
the owl was **not** at the oak grove. That place came from the schema, not
the note. The barn roof was not an available answer, so the model supplied
one that was. There was no parsing error to warn us.

This is the difference between **a valid record** and **a true record**.
Checking the shape can catch a missing count or an invalid place name. It
cannot tell you whether the place actually matches the observation.

## Give it a way to say “none of these”

Change one part of the schema: add `other` to the allowed places.

<DocsExample recipe="so-schema-other" />

With the barn note still in `note`, run the request again:

<CapturedAnswer set="structured-output" step="fixed" />

The owl is now under `other`, not at a location where it was never seen.
The hares are under `meadow` in this recorded answer; another model chose
`other` for “barn field.” Adding an escape hatch stopped the forced guess
about the roof, but it did **not** define where a barn field belongs. If
that distinction matters, define the places more carefully, or keep the
observer’s original location in a separate field. Do not treat `other` as
an exact location.

The same principle applies to species. In another recorded note, the
observer could not tell whether two deer were roe or fallow. The model
returned `"deer"`, not a guessed species. If your schema offers only
`"roe deer"` and `"fallow deer"`, it may force the guess the note avoided.

## Check what your provider did

An LM15 request can describe this shape across providers; that doesn’t mean
every provider can enforce it. In the recorded calls on 23 September 2026,
OpenAI, Anthropic, Gemini, and an OpenAI model through OpenRouter returned
the requested sighting shape. DeepSeek returned an error: it did not accept
this `json_schema` format. Z.AI returned Markdown when called through
Python: LM15 recorded that the schema was dropped, rather than pretending
it had been enforced.

The Z.AI outcome differs among LM15 languages today. R and Julia **refuse**
the unsupported schema before sending; Python and TypeScript **record that
they dropped it**. Either way, don’t save the answer as a sighting record on
the assumption that the provider honored the schema. Check what happened
for your provider and SDK. These are observations about the named models and
SDK versions, not a claim about every model offered by each provider.

Some providers offer an “any JSON” mode too. It asks for JSON, not *your*
fields. With that mode, DeepSeek returned valid JSON whose fields included
`location` and `notes`, not this page’s `place`. Choose it when any JSON is
what you want, not as a substitute for checking the shape of a station
record.

## Try it yourself

Predict before you run each change.

1. Leave `other` in the schema and use the deer note from the station. What
   should the species field say if the note can’t distinguish roe from fallow?
2. Remove `additionalProperties: false` from the item schema. What extra
   details might the model include? Would that preserve the limp? Would your
   program be ready to store the extra field?
3. Keep the original three places. Would a validator catch the owl’s wrong
   location? What could catch it instead?
